01 / JOB CARDS

오늘은 어떤 정비를 할까요?

각 명령은 독립적입니다. 필요한 작업 하나를 선택하세요.

환경 확인 / 앱 빌드 없음

규격에 맞는 공구가 있는지 먼저 확인합니다.

지정된 JDK의 버전·제조사와 SDK 플랫폼·빌드 도구의 존재를 확인하고 Android CLI·Gradle 버전을 출력합니다. 공구가 없으면 멈춥니다. 자동 설치나 라이선스 동의는 하지 않습니다.

bash script/android-light.sh doctor

저장소 루트에서 실행하세요. 이 페이지는 명령을 설명하고 복사만 하며 빌드를 실행하지 않습니다.

먼저 터미널에서 cd ~/Desktop/keelim-maestro/all · 명령을 생략하면 doctor, 앱을 생략하면 CNUBUS를 선택합니다.

02 / HOW THE HANGAR WORKS

공구를 고르고, 작업 지시서를 실행합니다.

어떤 명령을 골라도 먼저 공통 준비 상태를 확인합니다.

A / JDK

규격에 맞는 동력 장치

mise.toml의 Temurin 버전을 읽고 기존 mise 설치에서 찾습니다. 현재 규격은 17.0.20+8. 다른 위치라면 LIGHT_JAVA_HOME으로 같은 JDK를 지정합니다.

B / ANDROID CLI + SDK

공구함 위치와 부품 규격

android info sdk로 SDK를 찾습니다. 현재 SDK 플랫폼은 37.0, 확인하는 Build Tools는 36.0.0입니다. 기존 SDK 라이선스 폴더도 확인합니다.

C / GRADLE WRAPPER

정해진 작업 지시서

저장소의 ./gradlew가 실제 작업을 수행합니다. 현재 Gradle은 9.4.1. 선택한 앱과 그 앱에 필요한 공통 모듈을 처리합니다.

작업반은 작게, 일은 필요한 만큼

worker는 기본 최대 2개. 프로젝트 병렬 실행과 설정 캐시 병렬 처리를 끕니다. LIGHT_WORKERS=1 bash script/android-light.sh apk로 작업 수를 더 줄일 수 있습니다.

같은 작업장 안에서 처리하고 종료

Kotlin 컴파일은 Gradle 프로세스 안에서 처리합니다. 작업이 끝나면 일회성 Gradle 데몬도 종료합니다. 기존 Gradle 힙 설정은 2GiB이며, Mac 전체 메모리 상한은 아닙니다.

멀쩡한 부품은 다시 만들지 않습니다

캐시와 증분 빌드로 바뀌지 않은 작업 결과를 재사용합니다. 설정 캐시에는 작업 계획을 보관합니다. clean을 자동 실행하지 않으며, 첫 빌드에는 의존성 다운로드가 필요할 수 있습니다.

검사 기록도 재사용할 수 있습니다

test도 입력이 같으면 이전 통과 결과를 재사용할 수 있습니다. UP-TO-DATE는 이번에 테스트를 새로 실행했다는 뜻이 아닙니다. 아래 기록은 별도 재실행으로 확인했습니다.

시험대 검사 통과와 시험비행은 구분합니다.
실제 휴대폰에서의 화면·GPS·외부 서비스 동작은 검증하지 않았습니다. 다른 앱도 이번 기록의 검증 대상이 아닙니다. 기존 ASM 계측 경고가 남아 있습니다.
출력 파일과 구성의 한계 보기
  • APK: app-cnubus/build/outputs/apk/debug/app-cnubus-debug.apk
  • SDK 패키지를 자동 설치하거나 SDK 라이선스에 동의하지 않습니다. 라이선스 폴더 존재 확인은 유효한 동의 전체를 검증하는 절차가 아닙니다.
  • 기존 local.properties의 SDK 위치가 Android CLI의 위치와 다르면 수동 정렬이 필요합니다.
  • 빌드에는 기존 provider 설정이 필요할 수 있습니다. 에뮬레이터는 컴파일·APK 생성에 필요하지 않습니다.
  • 기준 도구: Android CLI 1.0.16625370 / AGP 9.2.1. 페이지는 정적 설명이며 현재 환경을 실시간 진단하지 않습니다.
